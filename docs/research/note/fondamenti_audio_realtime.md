## 1. Modello a callback (pull) contro I/O bloccante; come CoreAudio, PortAudio, JACK, ASIO e ALSA consegnano i buffer; accoppiamento di input e output nel full-duplex; anatomia di un ciclo

### Takeaway
Tutte le API a bassa latenza (CoreAudio, JACK, ASIO, ALSA via period, PortAudio in modalita' callback) funzionano a "pull": a ogni confine di periodo il driver sveglia un thread ad alta priorita' che riceve nello stesso ciclo un blocco di input appena catturato e un blocco di output da riempire prima della scadenza. Il full-duplex "vero" (un solo callback, un solo clock) si ottiene solo se input e output stanno sullo stesso device o su un aggregate device. Con due device separati servono due callback, un ring buffer in mezzo e una correzione del drift (varispeed o resampling adattivo).

### Cited Findings

#### PortAudio (modello, callback contro blocking)
- Uno stream PortAudio gestisce "at most one input device and one output device - streams may be full duplex or half duplex"; l'implementazione gestisce internamente i buffer e chiede l'elaborazione all'applicazione tramite un callback associato allo stream all'apertura (paper del 2001) — [Bencina & Burk, PortAudio, ICMC 2001](http://www.portaudio.com/docs/portaudio_icmc2001.pdf)
- Ciclo full-duplex: "When the stream is started, audio I/O begins and the user callback function is repeatedly called with a pointer to a full input buffer that is to be read, and a pointer to an empty output buffer that is to be filled. It is also passed a time-stamp that is the number of sample frames generated so far." — [Bencina & Burk 2001](http://www.portaudio.com/docs/portaudio_icmc2001.pdf)
- Scelta di progetto: callback invece di read/write bloccanti, perche' il callback fornisce un "thread" di sintesi in background in modo portabile; "The authors believe that callbacks are the preferred technique for portable APIs"; sopra l'API c'e' uno strato di blocking I/O pensato per programmi didattici (dato del 2001) — [Bencina & Burk 2001](http://www.portaudio.com/docs/portaudio_icmc2001.pdf)
- Esempio storico di full-duplex costruito con due callback: su Mac Sound Manager i dati del callback di input (SPBRecord) venivano scritti in un "atomic ring buffer", letti dal callback di output (SndDoCommand) e passati al callback utente, "This allows the user to process input data and output the result using a single callback function." — [Bencina & Burk 2001](http://www.portaudio.com/docs/portaudio_icmc2001.pdf)
- Firma V19 del callback: `int PaStreamCallback(const void *input, void *output, unsigned long frameCount, const PaStreamCallbackTimeInfo* timeInfo, PaStreamCallbackFlags statusFlags, void *userData)`; i buffer sono interleaved oppure, con `paNonInterleaved`, un buffer per canale; il callback "must always fill the entire output buffer irrespective of its return value"; valori di ritorno `paContinue` (0), `paComplete` (fine dopo aver suonato tutto l'output), `paAbort` (fine il prima possibile) — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)
- `framesPerBuffer`: con `paFramesPerBufferUnspecified` (0) il callback "will receive an optimal (and possibly varying) number of frames based on host requirements"; "With some host APIs, the use of non-zero framesPerBuffer for a callback stream may introduce an additional layer of buffering which could introduce additional latency"; si raccomanda un valore fisso "only be used when your algorithm requires a fixed number of frames per stream callback." — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)
- Semantica blocking: `Pa_ReadStream` non ritorna finche' l'intero buffer non e' pieno e restituisce `paInputOverflowed` se e' stato scartato input dalla chiamata precedente; `Pa_WriteStream` restituisce `paOutputUnderflowed` se e' stato inserito output; `Pa_GetStreamReadAvailable`/`WriteAvailable` danno i frame leggibili/scrivibili senza attesa; `Pa_GetStreamCpuLoad` vale 0.0 per gli stream bloccanti — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)
- Con il blocking I/O la granularita' di blocco "preferred block granularity" coincide idealmente con `framesPerBuffer`; il codice ad alte prestazioni dovrebbe leggere/scrivere blocchi di quella dimensione — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)

#### CoreAudio (HAL e AUHAL)
- Firma dell'IOProc: `OSStatus (AudioObjectID inDevice, const AudioTimeStamp* inNow, const AudioBufferList* inInputData, const AudioTimeStamp* inInputTime, AudioBufferList* outOutputData, const AudioTimeStamp* inOutputTime, void* inClientData)`, dichiarata con `__attribute__((nonblocking))`; "An AudioDeviceIOProc is called by an AudioDevice to provide input data read from the device and collect output data to be written to the device for the current IO cycle." — [Apple, AudioDeviceIOProc](https://developer.apple.com/documentation/coreaudio/audiodeviceioproc)
- Semantica dei timestamp nello stesso ciclo: `inNow` "indicates the IO cycle started ... includes any scheduling latency that may have been incurred waking the thread"; `inInputTime` "the time at which the first frame in the data was acquired from the hardware"; `inOutputTime` "the time at which the first frame in the data will be passed to the hardware"; all'ingresso la memoria di output "has been zeroed out"; il contenuto di input non va mai modificato; il valore di ritorno "should always be 0" — [Apple, AudioDeviceIOProc](https://developer.apple.com/documentation/coreaudio/audiodeviceioproc)
- Architettura a due processi: "For every audio server I/O thread, there is a second thread in the client application. We see here that the audio server wakes and waits for this thread on each I/O cycle." (WWDC 2020) — [Apple WWDC20 "Meet Audio Workgroups"](https://developer.apple.com/videos/play/wwdc2020/10224/)
- AUHAL: "An application can use the Hardware Abstraction Layer's (HAL) AudioOutputUnit to interface to a single audio device"; l'input va abilitato con `kAudioOutputUnitProperty_EnableIO` sull'element 1 (e il device si imposta solo dopo); i dati di input si ottengono nel callback registrato con `kAudioOutputUnitProperty_SetInputCallback` chiamando `AudioUnitRender` con un proprio `AudioBufferList` (TN2091, 2004, aggiornata 2014) — [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html)
- Due device distinti: "If you have two separate audio devices, two AUHALs will be required. However, because each AUHAL is going to run on its own separate I/O proc, you cannot make a direct connection between the two AUHALs. You must use a notification mechanism to notify the output device that data has arrived then pass the data through." — [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html)
- Il sample code CAPlayThrough (v1.2.2, 2013) usa "two instances of the AUHAL audio unit (one for input, one for output) and a varispeed unit in between to compensate for minor sample rate drift", piu' "a ring buffer to store the captured audio data from input" — [Apple CAPlayThrough](https://developer.apple.com/library/archive/samplecode/CAPlayThrough/Introduction/Intro.html)
- Dimensione del buffer di I/O: default storico 512 frame; con `kAudioHardwarePropertyPowerHint` (da OS X 10.9) il default sale a 4096; "An application has complete control over the size of the I/O buffer it uses" tramite `kAudioDevicePropertyBufferFrameSize` (HAL o AUHAL); il range legale si legge con `kAudioDevicePropertyBufferFrameSizeRange` (TN2321, 2013) — [Apple TN2321](https://developer.apple.com/library/archive/technotes/tn2321/_index.html)
- Un device riportato con massimo 4096 frame, non impostabile a 8192 — [JUCE forum](https://forum.juce.com/t/how-to-increase-aph-audio-settings-buffer-size-4096-samples-on-mac/58642) (solo snippet di ricerca)

#### ALSA, JACK, ASIO
- ALSA: "A frame is equivalent of one sample being played, irrespective of the number of channels or the number of bits"; "A period is the number of frames in between each hardware interrupt"; "The buffer is a ring buffer"; "The buffer size always has to be greater than one period size", di solito 2 periodi; buffer_size = period_size x periods; esempio: period di 4410 frame a 44.1 kHz stereo 16 bit -> un interrupt ogni 100 ms; "it is the ALSA runtime that decides on the actual buffer_size and period_size" — [ALSA, FramesPeriods](https://www.alsa-project.org/main/index.php/FramesPeriods)
- JACK: buffer = frame per periodo (`-p`) x periodi per buffer (`-n`); "JACK2 will add an implicit additional period when using the default asynchronous mode", quindi (n+1) x p invece di n x p — [jack_iodelay(1) man page](https://man.archlinux.org/man/extra/jack-example-tools/jack_iodelay.1.en)
- Regola JACK per il process callback (citata da Bencina): "The code in the supplied function must be suitable for real-time execution. That means that it cannot call functions that might block for a long time. This includes malloc, free, printf, pthread_mutex_lock, sleep, wait, poll, select, pthread_join, pthread_cond_wait, etc, etc." — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- "Typically, audio processing is done in periods — samples are processed in blocks of fixed size. In particular, all JACK-enabled applications work this way, and the situation is not really different when using ALSA directly." (LAC 2005) — [Adriaensen, Using a DLL to filter time](https://kokkinizita.linuxaudio.org/papers/usingdll.pdf)
- ASIO: schema "double-buffer" sincrono all'I/O (l'host lavora su una meta' mentre l'altra e' in uso); prima dell'avvio il driver emette uno o piu' `bufferSwitch()` per riempire i primi buffer di output con input a silenzio; "It can be assumed that the streaming will be constant after the third bufferSwitch callback"; `ASIOGetLatencies` include "buffering that goes beyond the double buffer e.g. used by USB driver designs" — [asio.h (copia in RtAudio)](https://git.kx.studio/falkTX/rtaudio/src/branch/releases/include/asio.h), [ASIO SDK 2.3 doc](https://www.scribd.com/document/332887768/ASIO-SDK-2-3-pdf), [patch Carla](https://git.kx.studio/falkTX/Carla/commit/6d1b4404c95ca89f229b637209a0ac1ec940561e.diff) (tutte solo snippet di ricerca; ASIO e' solo Windows, irrilevante per il Mac bersaglio)

#### Scadenza per ciclo
- Esempio numerico: buffer da 256 campioni a 44.1 kHz = callback a 179.26 Hz; "your callback would have to compute each and every buffer in less than 5.8 milliseconds ... Each and every buffer. No exceptions." (2011) — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)

### Inferences
- Anatomia di un ciclo per PGE (sintesi da IOProc, PortAudio e Bencina): (1) il driver/coreaudiod sveglia il thread I/O; (2) il callback legge timestamp e contatore di campioni e verifica la continuita' (sample time atteso = precedente + frameCount, altrimenti c'e' stato un xrun); (3) svuota, con un tetto al numero di messaggi, la FIFO dei comandi dal thread di controllo; (4) copia il blocco di input nel ring buffer di cattura (con eventuale DC blocker/HPF/gate); (5) avvia i grani con onset nel blocco all'offset giusto e rende tutti i grani attivi leggendo dal ring buffer; (6) protegge l'uscita (limiter o clip) e riempie sempre tutto il buffer di output; (7) pubblica meter e analisi su una FIFO di ritorno non bloccante (se e' piena, scarta); (8) ritorna ben prima della scadenza.
- In CoreAudio la latenza minima "attraverso" il ciclo e' implicita nei timestamp: `inOutputTime.mSampleTime - inInputTime.mSampleTime` da' la distanza in frame tra cattura del primo campione di input e presentazione del primo di output nello stesso ciclo (≥ 2 blocchi piu' i safety offset). Va verificato sperimentalmente su ogni device.
- Il blocking I/O sposta il problema della scadenza nel thread applicativo, che non e' a priorita' real-time, e PortAudio deve aggiungere un buffer interno: piu' latenza e piu' rischio di xrun. Per un sistema interattivo e' preferibile il callback, con il thread di controllo che comunica solo via FIFO e atomic.
- [Intel/Ventura] Microfono integrato e cuffie/uscita integrata appartengono di solito allo stesso dispositivo logico o a due device con lo stesso clock? Non verificato: se macOS li espone come due device distinti (input "MacBook Pro Microphone" e output "Speakers/Headphones"), il full-duplex in un solo IOProc richiede un aggregate device, oppure due IOProc con un ring buffer, come in CAPlayThrough.
- La dimensione fissa del blocco (`framesPerBuffer` diverso da 0) semplifica lo scheduling dei grani, ma su alcune host API aggiunge buffering. Conviene scrivere il motore in modo che accetti blocchi di dimensione variabile, con un massimo noto per la preallocazione.

### Gaps
- Range reale di `kAudioDevicePropertyBufferFrameSizeRange` del codec integrato di un Mac Intel sotto Ventura: non trovato in fonte verificabile. Un post della lista coreaudio-api, visto solo nel riassunto di ricerca, riportava 29-2304 frame a 96 kHz e 14-1152 a 44.1 kHz per un device; l'archivio lists.apple.com rispondeva 502 e il dato non e' verificabile. Va misurato a runtime.
- Se un buffer size richiesto da un processo valga per l'intero device o solo per quel client: TN2321 non lo dice. Non verificato.

- Struttura di ASIO verificata solo su snippet (manca il PDF dell'SDK); irrilevante per il Mac bersaglio.

## 2. Latenza: formule, input/output/round-trip, misura; soglie accettabili per l'interazione strumentale

### Takeaway
La latenza di ogni stadio e' (frame bufferizzati) / (sample rate). Il round-trip e' circa il buffering di input piu' quello di output piu' i safety offset e le latenze di device e convertitori, quindi almeno 2 blocchi piu' l'hardware. Obiettivo percettivo di riferimento: ≤ 10 ms azione-suono con jitter ≤ 1 ms (Wessel & Wright 2002); il jitter conta quanto la media. Per gesti continui e non percussivi la letteratura ammette 20-30 ms (Lago & Kon 2004). Le misure del 2016 mostrano che molte catene reali stanno sopra 10 ms e tutte avevano jitter sopra 1 ms, quantizzato alla dimensione del blocco.

### Cited Findings

#### Formule e numeri di riferimento
- 256 campioni a 44.1 kHz = 5.8 ms; "~1ms buffers (say 64 samples at 44100Hz) would be considered pretty good but not necessarily ideal"; buffer da 1-5 ms "normal and achievable" con CoreAudio, ASIO, WASAPI, ALSA, JACK; alcuni hardware arrivano a 16 campioni (circa 1/3 ms a 44.1 kHz); Android circa 50 ms e WMME circa 30 ms come casi ad alta latenza (dati 2011) — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- "an end-to-end system response of less than 8ms including all system latencies (not just audio latency) is not an unreasonable ballpark number for interactive systems. For live audio effects processing many users would prefer latency to be much lower than this." — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Relazione uno a uno su macOS: "The size of the I/O buffer is directly related to the latency of the I/O system. It is a one to one relationship. For each sample frame the I/O buffer size is increased there is a corresponding increase of one sample frame more latency." — [Apple TN2321](https://developer.apple.com/library/archive/technotes/tn2321/_index.html)
- Componenti della latenza CoreAudio: latenza del device (`kAudioDevicePropertyLatency`, per scope input/output), safety offset (`kAudioDevicePropertySafetyOffset`) e latenza dello stream (`kAudioStreamPropertyLatency`). JUCE ha aggiunto il safety offset nel novembre 2015 perche' la somma era "very close" al round-trip misurato; nel 2018 la latenza dello stream risultava sempre zero nei test; nel 2015 il block size era incluso in modo incoerente tra il device integrato di un iMac e una Steinberg UR22 — [JUCE forum, Audio Device latencies & safety offsets on Mac](https://forum.juce.com/t/audio-device-latencies-safety-offsets-on-mac/15647)
- Descrizione di Jeff Moore (Apple): la latenza di un canale e' "the sum of the device latency and the latency of the stream the channel is in", con safety offset e buffer frame size da sommare ai timestamp dell'IO; un post del 2013 avverte che includere il safety offset con AUHAL (invece del HAL diretto) sovrastimava molto il ritardo — [coreaudio-api 2010](https://lists.apple.com/archives/coreaudio-api/2010/Jan/msg00046.html), [coreaudio-api 2013](https://lists.apple.com/archives/coreaudio-api/2013/May/msg00040.html) (solo snippet di ricerca; archivio non raggiungibile, HTTP 502)
- I device integrati di macOS possono mostrare latenza aggiuntiva oltre a quella dichiarata, forse per elaborazioni interne come la riduzione del rumore — [JUCE forum, macOS Round Trip Latency](https://forum.juce.com/t/macos-round-trip-latency/45278) (solo snippet di ricerca; attribuzione del thread non certa)
- Distanza acustica: "one sample at 48 kHz corresponds to about 7 millimeters in air" — [Adriaensen, Controlling adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)

#### Misura
- `jack_iodelay`: serve un cavo di loopback fisico dall'uscita all'ingresso, "This creates a roundtrip that goes through any analog-to-digital and digital-to-analog converters"; "accurate to a resolution of greater than 1 sample"; il risultato "will include the JACK buffer length"; sottraendo n x p (o (n+1) x p con JACK2 asincrono) si ottiene la latenza "extra" dell'hardware, da dividere per due per i parametri -I/-O — [jack_iodelay(1)](https://man.archlinux.org/man/extra/jack-example-tools/jack_iodelay.1.en)
- Esempio reale: 48 kHz, 64 frame x 2 periodi -> "235.286 frames 4.902 ms total roundtrip latency, extra loopback latency: 43 frames" — [Blokas community](https://community.blokas.io/t/latency-measurment-with-jack-iodelay/1785/1) (solo snippet di ricerca)
- Metodo azione-suono di McPherson et al.: un tester genera un evento sul pin del dispositivo e misura l'arrivo del click; circa 1000 prove separate da 250 ms; jitter = massimo meno minimo dopo aver scartato il 2.5% superiore e inferiore — [McPherson, Jack & Moro, NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)

#### Soglie percettive
- Wessel & Wright (CMJ 2002): "We place the acceptable upper bound on the computer's audible reaction to gesture at 10 milliseconds (ms) and the systems described in this paper provide for measured latencies nearer 7 ms"; "Low variation of latency is critical and we argue that the range of variation should not exceed 1 ms." — [Wessel & Wright 2002, versione arXiv](https://arxiv.org/pdf/2010.01570) (citazioni dallo snippet di ricerca; il 10 ms e' confermato da McPherson 2016)
- McPherson et al. (2016) adottano il 10 ms di Wessel come riferimento ma "we suspect that the ideal threshold may be much lower for percussive musical interactions"; citano: variazioni di tapping intorno a 4 ms, asincronia di 6 ms rilevabile, theremin con soglia minima di 20-30 ms, sincronizzazione mantenuta fino a 55 ms di latenza (Dahl & Bresin), batteristi professionisti con errore medio di 2 ms (1 ms a 300 ms di IOI); "any system with jitter less than 1ms would be sufficient for even the most stringent scenarios"; "While users can compensate for static latency [3], unpredictable variation cannot be corrected." — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- Lago & Kon (ICMC 2004, anno dedotto dal nome del file): "somewhat high latencies (around 20–30ms) are probably perfectly acceptable for typical musical applications"; il timbro dei flam cambia gia' con 1 ms; tapping con variazioni di 4 ms e rilevamento cosciente a circa 6 ms; tra percussioni e archi di un'orchestra ci sono oltre 10 m, cioe' circa 30 ms; asincronie fino a 50 ms normali nella musica da camera; tasto-onset del pianoforte circa 100 ms (circa 30 ms per staccato forte); variazioni di 20 ms del ritardo di feedback compensate inconsciamente; ridurre il jitter anche a costo di piu' latenza "is usually a good strategy" — [Lago & Kon, The Quest for Low Latency](https://users.ime.usp.br/~kon/papers/icmc04-latency.pdf)
- Jack et al. (Audio Mostly 2016): nel loro studio la stabilita' della latenza contava quanto il suo valore basso — [Jack, Stockman & McPherson 2016](https://instrumentslab.org/data/andrew/jack_am2016.pdf) (solo snippet di ricerca)

#### Misure su sistemi reali (dati 2016, in parte su Mac Intel)
- Banco di prova: audio integrato di un MacBook Pro mid-2014 (Core i7 2.7 GHz, OS X 10.10.5); Max/MSP su CoreAudio nativo, Pd su PortAudio, Pd al minimo di 64 campioni — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- Max/MSP a blocco 32: miglior seriale 8.2 ms di media ma oltre 10 ms nel 12% dei casi; MIDI con overdrive 5.1 ms di media (6.4 ms senza); Pd a blocco 64: 9.0 ms con MIDI e "callbacks enabled", 16.8 ms in seriale; Pd su JACK 18.7 ms con 10 ms di jitter; "Jitter was above 1ms in every configuration tested"; "jitter tends to be at intervals of the hardware audio block size, meaning that using smaller audio blocks improves both raw latency and jitter." — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- USB peggiora la latenza: viene citato l'intervallo di frame di 1 ms del full-speed USB; un'interfaccia Behringer UCA222 superava 45 ms in ogni caso; una Focusrite USB su Raspberry Pi arrivava a 11.7 ms con 3.0 ms di jitter; misure desktop di Wang et al. (2010) da poco piu' di 3 ms a 70 ms secondo OS e driver; "The lowest latencies typically require small hardware buffer sizes which are prone to dropouts as system load increases." — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- Bela (Xenomai, PRU): blocchi fino a 2 campioni a 44.1 kHz (46 µs) senza underrun, latenza sotto 1 ms, jitter ≤ 23 µs — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)

### Inferences
- Durata di un blocco (frame / fs), calcolata: 32 -> 0.667 ms a 48 kHz (0.726 ms a 44.1 kHz); 64 -> 1.333 (1.451); 128 -> 2.667 (2.902); 256 -> 5.333 (5.805); 512 -> 10.667 (11.610); 1024 -> 21.333 (23.220). A 48 kHz e 128 frame il callback gira a 375 Hz.
- Bilancio indicativo per PGE a 48 kHz e 128 frame: 2.67 ms di input + 2.67 ms di output = 5.3 ms, piu' safety offset e latenze di device e convertitori (da misurare), piu' la distanza acustica (1 m ≈ 143 campioni ≈ 2.98 ms, derivato dai 7 mm per campione di Adriaensen). Con le cuffie la distanza e' trascurabile. Per stare sotto 10 ms azione-suono con altoparlanti a 1-2 m servono 64-128 frame e un hardware con poca latenza extra.
- Formula operativa per CoreAudio (da verificare con loopback): L_in = buffer + safety_in + device_latency_in (+ stream_latency_in); L_out = buffer + safety_out + device_latency_out (+ stream_latency_out); RTL = L_in + L_out. Le fonti divergono sul safety offset con AUHAL, quindi va sempre misurato con un cavo o con un impulso nel campo acustico.
- Il jitter quantizzato alla dimensione del blocco (McPherson) indica che gli eventi di controllo vanno applicati con un timestamp e un offset dentro il blocco, non all'inizio del blocco successivo. Cosi' il jitter diventa una latenza costante, il compromesso raccomandato da Lago & Kon (vedi sezione 6).
- Per un granulatore pilotato da gesti continui la soglia di 20-30 ms e' probabilmente tollerabile. Per trigger percussivi di grani conviene puntare a ≤ 10 ms e soprattutto a jitter < 1 ms.

- Strumenti di misura del round-trip specifici per macOS: non ricercati. `jack_iodelay` richiede JACK; in alternativa si puo' scrivere un misuratore con impulso e cross-correlazione.

## 3. Regole di sicurezza real-time per il thread audio

### Takeaway
Regola cardinale (Bencina 2011): "If you don't know how long it will take, don't do it." Nel callback: niente allocazione o deallocazione, niente mutex (priority inversion, sezioni critiche non limitate, interazione con lo scheduler), niente I/O su file o rete e niente printf/NSLog/GUI, niente syscall bloccanti o attese su altri thread, niente algoritmi con caso peggiore non limitato o ammortizzato, niente codice di terzi non fidato. Attenzione anche a page fault e garbage collector. Doumler (2020) aggiunge che `std::mutex` non va usato nemmeno con `try_lock`.

### Cited Findings
- Elenco di Bencina (2011, aggiornato il 13 agosto 2011): "Don't allocate or deallocate memory; Don't lock a mutex; Don't read or write to the filesystem or otherwise perform i/o. (In case there's any doubt, this includes things like calling printf or NSLog, or GUI APIs.); Don't call OS functions that may block waiting for something; Don't execute any code that has unpredictable or poor worst-case timing behavior; Don't call any code that does or may do any of the above; Don't call any code that you don't trust to follow these rules; On Apple operating systems follow Apple's guidelines" — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Cosa fare: algoritmi con buon caso peggiore ("ideally O(1)"), ammortizzare il calcolo su molti campioni invece di algoritmi "bursty", preallocare e precalcolare in un thread non critico, usare strutture dati possedute solo dal callback — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Priority inversion: se il thread GUI tiene un lock, il callback deve attendere il thread GUI, che puo' essere preemptato da qualunque altro processo; uno spin lock fatto in casa ha lo stesso problema se il thread atteso ha priorita' piu' bassa; la priority inheritance (PREEMPT_RT, `PTHREAD_PRIO_INHERIT` su Linux dal 2.6.18, 2006) non e' portabile — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Un lock rende la sezione critica altrui parte del caso peggiore del callback, per esempio un `push_back` su `std::vector` che rialloca e copia; "justified scheduler paranoia": gli scheduler general purpose non garantiscono comportamento real-time, quindi meglio non chiamare primitive di sincronizzazione nel callback — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Trylock: "you can't use it to protect anything that you must access at every callback"; nel caso peggiore il lock non si acquisisce mai — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Allocazione: l'allocatore puo' prendere lock, chiedere memoria all'OS (che puo' paginare su disco) e usare algoritmi di durata imprevedibile; soluzioni: preallocare, allocare solo fuori dal thread audio, oppure un allocatore deterministico usato solo dal callback (SuperCollider usa un allocatore alla Doug Lea solo nel callback; AudioMulch usa pool per thread e carica i plugin nel thread UI) — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Cose invisibili: GC di Java/C#; page fault della memoria virtuale, da cui la valutazione di `mlock()`; il disco ha in media circa 8 ms di seek; "assume that all system API functions could allocate memory, use locks or employ algorithms with poor worst-case time behavior"; perfino `mach_absolute_time()` e' un'eccezione di cui l'autore non e' "100% confident" — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Apple: "don't call the BSD layer from your IOProc"; anche Objective-C e i CoreFrameworks sono esclusi; Jeff Moore: chiamate bloccanti al HAL e NSLog "allocates memory and blocks in fun and unexpected ways ... Doing any of these will eventually cause glitching." — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Esempio di picco limitato ma pericoloso: azzerare con `memset` una delay line grande nel callback; meglio distribuire il lavoro su piu' callback — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- PortAudio: "Do not allocate memory, access the file system, call library functions" o altre funzioni dal tempo imprevedibile; dal callback si puo' chiamare solo `Pa_GetStreamCpuLoad()` — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html), [PortAudio, Writing a Callback](http://files.portaudio.com/docs/v19-doxydocs/writing_a_callback.html)
- Doumler (14 aprile 2020): niente `std::mutex` sul thread audio, "not even with try_lock", perche' l'`unlock()` (anche dal distruttore di `std::unique_lock`) puo' richiedere una syscall per svegliare un waiter. Soluzioni preferite: `std::atomic`, FIFO SPSC lock-free, strutture immutabili; ripiego: spinlock su `std::atomic_flag` in cui il thread audio chiama solo `try_lock()` con un'alternativa in caso di fallimento, mentre il lato non audio fa back-off progressivo (spin, poi `_mm_pause()`, poi `yield` occasionale). Scartati `yield` in loop stretto e C++20 `atomic::wait/notify`, perche' `notify_one()` puo' essere implementato con una syscall — [Doumler 2020](https://timur.audio/using-locks-in-real-time-audio-processing-safely)
- Misure di Doumler [Intel]: Intel i9 6-core 2.9 GHz (Dell XPS e MacBook Pro); un'iterazione di spin circa 5 ns, `_mm_pause()` circa 39 ns, `yield` 230-510 ns secondo l'OS; sotto carico pesante, ritardi occasionali di `yield` di 10-30 ms circa ogni pochi secondi; taratura finale: 5 spin, 10 pause, poi 3000 iterazioni da 10 pause (circa 1 ms) prima di un `yield`. Nei commenti Rigtorp suggerisce su Linux mutex futex con priority inheritance e SCHED_FIFO — [Doumler 2020](https://timur.audio/using-locks-in-real-time-audio-processing-safely)
- Un thread Mach real-time che supera ripetutamente il budget dichiarato "is penalized (and may even be knocked down to normal thread priority)"; "this is soft real-time" (documento d'archivio, 2013) — [Apple Kernel Programming Guide, Mach Scheduling](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/KernelProgramming/scheduler/scheduler.html)
- Esistono i talk ADC 2019 "Real-time 101 - part I: Investigating the real-time problem space" e "Real-time 101 - Part II: The real-time audio developer's toolbox" di Fabian Renn-Giles e Dave Rowland (titoli verificati via YouTube oEmbed, contenuto non visionato) — [ADC19 parte I](https://www.youtube.com/watch?v=Q0vrQFyAdWI), [ADC19 parte II](https://www.youtube.com/watch?v=PoZAo2Vikbo)
- La libreria farbot di Renn-Giles (presentata a Meeting C++ 2019) offre `RealtimeObject`, `fifo` e `AsyncCaller` per spostare logging e deallocazione fuori dal thread real-time — [farbot README](https://github.com/hogliux/farbot)

### Inferences
- Per PGE: tutto cio' che cresce (grani, eventi, buffer di finestra) va dimensionato al massimo e preallocato all'avvio, con un pool di grani a capacita' fissa e una freelist O(1). Se il pool e' pieno, il nuovo grano si scarta (o si ruba il piu' vecchio) e si incrementa un contatore letto dalla UI, senza mai allocare.
- Il logging dal thread audio passa da una FIFO verso un thread logger; niente `print` nel callback.
- Bencina segnala i runtime con garbage collector e interpreti tra le "cose invisibili". Un callback scritto in un linguaggio con allocazione implicita (refcount, GC, lock interni dell'interprete) viola per costruzione le regole 1, 2 e 5. Questa e' una conseguenza di progetto, non un dato sulle librerie Python, che non sono in questo perimetro.
- Le finestre dei grani vanno precalcolate (tabelle). Cambi di configurazione pesanti (ricalcolo di tabelle, nuovi buffer) si preparano nel thread di controllo e si consegnano al thread audio come puntatore pronto (vedi sezione 4).

## 4. Comunicazione tra thread: ring buffer SPSC lock-free, atomic, double/triple buffering, code di messaggi, deallocazione differita; wait-free contro lock-free

### Takeaway
Lo schema consolidato e': FIFO SPSC lock-free per i comandi ordinati (controllo -> audio) e per i dati di ritorno (audio -> UI); `std::atomic` per i singoli parametri scalari; triple buffer o oggetti tipo `RealtimeObject` per pubblicare "l'ultimo stato" di strutture piu' grandi; deallocazione differita su un thread non real-time (garbage queue o AsyncCaller). Il requisito pratico e' che il lato real-time sia wait-free, cioe' completi sempre in un numero limitato di passi, anche se l'altro lato e' solo lock-free.

### Cited Findings
- Bencina: "the best practice is to use lock-free FIFO queues to communicate commands and data between real-time and non-real-time contexts"; PortAudio offre una coda lock-free come base; alternative: altre strutture non bloccanti, accesso atomico ("requires great care"), trylock — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- PortAudio ha rimosso dall'API i metodi Lock/Unlock perche' non implementabili su tutte le piattaforme; "It is recommended that applications use atomic data structures such as FIFOs for communication between the main program and the audio processing callback. This technique is used in JSyn, and other applications, and has proven to be both robust and portable." (2001) — [Bencina & Burk 2001](http://www.portaudio.com/docs/portaudio_icmc2001.pdf)
- `PaUtilRingBuffer`: "Single-reader single-writer lock-free ring buffer"; "N must be a power of two" (`PaUtil_InitializeRingBuffer` restituisce -1 altrimenti); `bigMask` "Used for wrapping indices with extra bit to distinguish full/empty", `smallMask` "Used for fitting indices to buffer"; `GetRingBufferWriteRegions/ReadRegions` restituiscono fino a due regioni contigue, poi si chiama `Advance...Index`; autore Phil Burk, "modified for SMP safety on OS X by Bjorn Roche" — [pa_ringbuffer.h](https://raw.githubusercontent.com/PortAudio/portaudio/master/src/common/pa_ringbuffer.h)
- `jack_ringbuffer`: accesso simultaneo sicuro per un solo lettore e un solo scrittore, con ruoli non scambiabili; `jack_ringbuffer_reset()` "is not thread safe"; `jack_ringbuffer_mlock()` usa `mlock()` e "is not a realtime operation"; `get_read_vector`/`get_write_vector` restituiscono due segmenti per lo spazio spezzato dal wrap-around, seguiti da `read_advance`/`write_advance`; `peek` legge senza avanzare — [JACK ringbuffer.h](https://jackaudio.org/api/ringbuffer_8h.html)
- Note di Bencina sul lock-free: evitare i lock evita la priority inversion senza scheduler real-time; "With the exception of a uniprocessor implementation of a single-reader single-writer ring buffer FIFO, all the lock-free algorithms which I have encountered require the use of special atomic processor instructions such as CAS ... or LL/SC" e richiedono memory barrier sui multiprocessori; la FIFO SPSC atomica e' presente in PortAudio, PortMidi, SuperCollider e JSyn — [Bencina, Some notes on lock-free and wait-free algorithms](http://www.rossbencina.com/code/lockfree)
- Terminologia: Bencina usa "lock free" come termine generico e ammette "I should have said 'wait free' or 'obstruction free'"; "In practice it has been shown that some non-blocking algorithms perform better than truly wait-free algorithms in low-contention scenarios" — [Bencina 2011, commenti](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- farbot: `RealtimeObject` con due modalita', `nonRealtimeMutatable` (per esempio coefficienti biquad scritti dalla UI e letti dall'audio) e `realtimeMutatable` (per esempio uno spettro calcolato in audio e mostrato dalla UI); `fifo` "will never lock nor block", con produttore e consumatore single o multiple, pop wait-free se il consumatore e' singolo o usa `overwrite_or_return_default`, ma con overwrite "the ordering of the FIFO is lost"; `AsyncCaller::callAsync` esegue una lambda su un thread non real-time, con logging e deallocazione come esempi — [farbot README](https://github.com/hogliux/farbot)
- Doumler: per i dati condivisi complessi, strutture immutabili, cioe' il thread di controllo copia e modifica mentre l'audio continua a leggere la versione vecchia; nei commenti: FIFO per i dati ordinati, atomic o triple buffer per pubblicare solo l'ultimo stato — [Doumler 2020](https://timur.audio/using-locks-in-real-time-audio-processing-safely)
- Un caricamento non limitato (plugin) va fatto nel thread UI, poi il risultato si consegna al callback: "sometimes it's OK to make the user wait, so long as the audio callback doesn't have to." — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Una coda lock-free usata per il resampling adattivo deve mantenere sempre contatori di lettura/scrittura corretti e permettere letture/scritture logiche di qualsiasi numero di elementi, anche negativo — [Adriaensen, Controlling adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)

### Inferences
- Definizioni standard (letteratura Herlihy, non verificate qui): un algoritmo e' lock-free se almeno un thread progredisce in un numero finito di passi, ed e' wait-free se ogni thread completa la propria operazione in un numero limitato di passi. Per l'audio conta la garanzia sul solo lato real-time: una FIFO SPSC con indici atomici e' wait-free su entrambi i lati, perche' nessuno ritenta in loop.
- Proposta di canali per PGE:
  1. parametri continui (densita', pitch, posizione) come `atomic<float>` scritti dal controllo e letti una volta per blocco, con smoothing nel thread audio per evitare zipper;
  2. FIFO SPSC di comandi a dimensione fissa (struct POD con tipo, target, valore, timestamp in campioni), svuotata a inizio callback con un limite massimo per ciclo;
  3. FIFO di ritorno (meter, posizione del write head, conteggi di xrun e di grani scartati) che il thread audio riempie con `try_push` e che scarta se e' piena;
  4. scambio di strutture pesanti (nuove tabelle di finestra, configurazioni di stream) con un puntatore atomico: il controllo prepara la nuova versione, l'audio la adotta con uno scambio a inizio blocco e rimette la vecchia in una FIFO "garbage" che il controllo libera. E' uno schema tipo RCU.
- Ordinamento della memoria: indici con semantica acquire/release (C++11 o equivalente). E' la ragione per cui PortAudio ha richiesto la modifica "for SMP safety on OS X"; il dettaglio delle barriere non e' stato verificato oltre questa nota.

### Gaps
- Non sono stati aperti i talk di Doumler su RCU o "Thread synchronisation in real-time audio processing" ne' la libreria crill. Mancano anche dati quantitativi sul costo di atomic e FIFO su x86 rispetto ad ARM.

## 5. Buffer circolari come struttura dati centrale: puntatori, wrap-around, potenze di due e maschere, letture frazionarie, delay line

### Takeaway
Il ring buffer e' la struttura dati ricorrente a ogni livello: il buffer hardware ALSA, le FIFO tra thread, la delay line e il buffer di cattura del microfono da cui leggono i grani. Con dimensione 2^k il wrap-around e' un AND con la maschera. Contatori monotoni non mascherati, con un bit in piu' o a 64 bit, distinguono pieno da vuoto e reggono l'overflow, perche' si usano solo le differenze. Le letture a posizione frazionaria richiedono interpolazione: lineare in generale, allpass dentro i loop di feedback.

### Cited Findings
- "The buffer is a ring buffer" (buffer hardware ALSA diviso in period) — [ALSA, FramesPeriods](https://www.alsa-project.org/main/index.php/FramesPeriods)
- Ring buffer PortAudio: N potenza di due; `bigMask` per gli indici "with extra bit to distinguish full/empty"; `smallMask` per l'indicizzazione nel buffer — [pa_ringbuffer.h](https://raw.githubusercontent.com/PortAudio/portaudio/master/src/common/pa_ringbuffer.h)
- Accesso senza copia a cavallo del wrap: due segmenti; il primo ha sempre `len` valido (anche zero), il secondo e' non vuoto solo se lo spazio e' spezzato — [JACK ringbuffer.h](https://jackaudio.org/api/ringbuffer_8h.html)
- Contatori: nel controllo del resampling i contatori `kJ, kA0, kA1` sono interi che "will overflow at some time. Since we only ever take differences of those, the overflow doesn't matter", ma la differenza va fatta in aritmetica intera prima di convertire in floating point — [Adriaensen, Controlling adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)
- Delay line variabili: "some form of interpolation between samples is usually required to avoid 'zipper noise' in the output signal as the delay length changes"; l'interpolazione lineare e' "very straightforward and inexpensive" e "sounds very good when the signal bandwidth is small compared with half the sampling rate"; l'allpass del primo ordine "costs the same as linear interpolation" ed e' preferibile nei loop di feedback — [J.O. Smith, PASP, Delay-Line Interpolation](https://ccrma.stanford.edu/~jos/pasp/Delay_Line_Interpolation.html)
- L'interpolazione lineare e' un filtro FIR "one-zero" con errore nullo in DC per ogni ritardo frazionario e piu' accurato alle basse frequenze ("sounds best when the signal is oversampled"); con ritardo frazionario variabile nel tempo diventa un filtro lineare tempo-variante; gli errori di ampiezza "can be highly audible" in un loop di feedback con guadagno vicino a 1, dove l'allpass elimina l'errore di ampiezza al prezzo di un errore di ritardo — [J.O. Smith, PASP, linear interpolation](https://ccrma.stanford.edu/~jos/pasp/Fractional_Delay_Filtering_Linear.html)
- Azzerare una delay line grande con `memset` nel callback puo' superare la scadenza; meglio distribuire l'azzeramento su piu' callback — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)

### Inferences
- Implementazione minima (pseudocodice): `buf[w & MASK] = x; w += 1;` (con `w` uint64 monotono). Per leggere un ritardo D frazionario: `p = w - D; i = floor(p); f = p - i; y = buf[i & MASK] + f * (buf[(i+1) & MASK] - buf[i & MASK])`, la forma a una moltiplicazione dell'interpolazione lineare tra i campioni n-M e n-M-1. Per interpolatori di ordine piu' alto (Lagrange, sinc) si leggono piu' campioni intorno a `i` e si riserva un margine pari alla meta' della lunghezza del kernel.
- Dimensionamento del buffer di cattura live: 2^19 = 524288 frame ≈ 10.92 s a 48 kHz (2 MiB in float32 mono); 2^20 ≈ 21.85 s (4 MiB); 2^21 ≈ 43.69 s (8 MiB). La maschera rende il costo di indicizzazione costante e senza branch.
- Vincolo del read head per la granulazione live: un grano con rapporto di lettura r (pitch) e durata L (campioni di output), che parte D campioni dietro il write head, consuma r·L campioni di input mentre il write head avanza di L. Per non superare il write head serve D > (r − 1)·L + margine (blocco + meta' kernel di interpolazione) quando r > 1. Quando r < 1 il grano si allontana e serve D + (1 − r)·L < dimensione del buffer − margine, per non leggere dati gia' sovrascritti.
- Il write head (contatore a 64 bit) e' anche il riferimento temporale naturale per le posizioni dei grani: posizione = sample time di cattura, coerente con il contatore della sezione 6.

### Gaps
- Confronto quantitativo di qualita' e costo tra interpolazione lineare, Lagrange di ordine 3 e sinc finestrata per il pitch-shifting dei grani: non ricercato (fuori perimetro: algoritmi di granulazione).

## 6. Timing sample-accurate degli eventi dentro un blocco; contatore di campioni come base dei tempi; clock audio contro clock di sistema; drift tra device

### Takeaway
La base dei tempi del motore deve essere il contatore di campioni dello stream, non l'orologio da parete. Gli eventi portano un timestamp in campioni; a ogni callback si convertono in offset dentro il blocco (ordinati) e si applicano a quell'offset, spezzando il blocco o avviando il grano a meta' blocco. Per tradurre il tempo di sistema (gesti, OSC, MIDI) in tempo-campione si usa un filtro DLL che rimuove il jitter di risveglio. Device con clock diversi sono "incoerenti" e richiedono resampling adattivo, oppure un aggregate device con drift correction.

### Cited Findings
- CLAP: `uint32_t time; // sample offset within the buffer for this event`; "The host will deliver these sorted in sample order"; il plugin deve inserire gli eventi in uscita "in sample sorted order"; le note expression "are delivered as sample accurate events and should be applied at the sample when received"; aggiornamenti di trasporto dentro il blocco come nuovi eventi — [CLAP events.h](https://github.com/free-audio/clap/blob/main/include/clap/events.h)
- VST3: "The only way for a parameter change to arrive in the processor is the processing call"; i punti di automazione "are sorted per offset (position inside the audio block)"; "The host always transmits value changes in a way that allows a sample-accurate reconstruction"; e' il plugin a scegliere quanto calcolo spendere per l'accuratezza, perche' l'automazione sample-accurate richiede di calcolare il valore DSP per ogni campione — [Steinberg VST3, Parameters and Automation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- Senza timestamp, il jitter si presenta "at intervals of the hardware audio block size" — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- PortAudio: `timeInfo` contiene i timestamp della cattura ADC del primo campione di input, dell'uscita DAC del primo campione di output e dell'invocazione del callback, in secondi, sincronizzati con `Pa_GetStreamTime()`, che e' "monotonically increasing" con origine non specificata — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)
- CoreAudio: `AudioTimeStamp` con `mSampleTime` ("The absolute sample frame time"), `mHostTime` ("The host machine's time base"), `mRateScalar` ("The ratio of actual host ticks per sample frame to the nominal host ticks per sample frame"), `mWordClockTime`, `mSMPTETime` e `mFlags`, che indica quali campi sono validi — [Apple, AudioTimeStamp](https://developer.apple.com/documentation/coreaudiotypes/audiotimestamp)
- Problema del clock (Adriaensen, LAC 2005): leggere il timer di sistema a ogni periodo e' affetto da ritardo interrupt-lettura, jitter, quantizzazione del timer ed errori di frequenza di campionamento, perche' "On most hardware, the sample clock is not locked in any way to the one that drives the system timer"; mappa ingenua t = t0 + (n − n0)·T, discontinua e anche non monotona — [Adriaensen, Using a DLL to filter time](https://kokkinizita.linuxaudio.org/papers/usingdll.pdf)
- DLL del secondo ordine: ω = 2πB/F (F = frequenza dei periodi, B = banda), b = √2·ω, c = ω² (il simbolo √ e' parzialmente perso nell'estrazione del testo); inizializzazione (anche "after an xrun"): `e2 = tper; t0 = read_timer(); t1 = t0 + e2;`; a ogni periodo: `e = read_timer() - t1; t0 = t1; t1 += b*e + e2; e2 += c*e;`. Il DLL riduce il jitter "by a factor of 100", per esempio da ±2 ms a circa ±10 µs su una scheda USB, dove il jitter di periodo arriva a 4 ms (contro 1 ms teorico del periodo di interrupt USB); con le schede PCI il risultato filtrato e' sotto il microsecondo — [Adriaensen 2005](https://kokkinizita.linuxaudio.org/papers/usingdll.pdf)
- Clock incoerenti (due schede senza word clock comune o audio in rete): "A fixed resampling ratio, e.g. 44100/48000, or even one that takes known errors into account, will sooner or later require samples to be inserted or dropped and this is in general not acceptable"; il problema vero e' controllare il rapporto partendo da timestamp rumorosi — [Adriaensen, Controlling adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)
- Numeri dell'implementazione zita-a2j/j2a: banda del loop circa 0.05 Hz; primi 4 s a banda piu' alta; stabilizzazione in circa 15 s (test 48 kHz contro 44.1 kHz), poi variazioni < 0.5° picco-picco a 1 kHz (1° = 2.78 µs); battimento di circa 0.012 Hz tra le frequenze di periodo delle due schede (ogni circa 83 s gli interrupt coincidono); il ritardo totale e' la somma dei frame nei due buffer hardware, nella coda lock-free e nel resampler; piccole variazioni graduali del ritardo non si notano, mentre una modulazione del ritardo con componenti ad alta frequenza produce "parasitic signals, noise or distortion", come il jitter di clock di un convertitore — [Adriaensen, Controlling adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)
- macOS: in un aggregate device si sceglie un "Clock Source" (il device col clock piu' affidabile) e si attiva "Drift Correction" per ogni altro device, tranne quelli collegati via word clock (pagina del 29 novembre 2023, immagini di Monterey) — [Apple Support, Aggregate Device](https://support.apple.com/en-us/102171)
- CAPlayThrough compensa il drift tra due device con un'unita' varispeed tra due AUHAL — [Apple CAPlayThrough](https://developer.apple.com/library/archive/samplecode/CAPlayThrough/Introduction/Intro.html)

### Inferences
- Ricetta per PGE:
  1. contatore `uint64 sample_clock` incrementato di `frameCount` a ogni callback (o letto da `mSampleTime`);
  2. il thread di controllo stima "ora in campioni" con il DLL (host time -> sample time, aggiornato dal callback via atomic) e timbra ogni evento con `t_target = now_samples + L_sched`, dove L_sched ≥ 1 blocco e' una latenza di scheduling fissa che trasforma il jitter in ritardo costante;
  3. il callback sposta gli eventi dalla FIFO in una coda di eventi futuri preallocata e ordinata, e per ogni evento con `block_start ≤ t < block_start + N` usa `offset = t − block_start`;
  4. per i grani basta far partire il loop di sintesi del grano a `offset`; per i parametri, o si spezza il blocco in sotto-blocchi agli offset o si interpola a rampa tra i punti (come in VST3);
  5. gli eventi "in ritardo" (t < block_start) si eseguono a offset 0 e si contano.
- Su macOS host time = `mach_absolute_time` e `mHostTime` e' nella stessa base, quindi la coppia (`mSampleTime`, `mHostTime`) di ogni ciclo e' l'input naturale del DLL e `mRateScalar` stima gia' il rapporto reale. Il legame preciso con `mach_absolute_time` non e' stato verificato nel dettaglio.
- Esempio illustrativo del DLL: a 48 kHz e 128 frame F = 375 Hz; con B = 1 Hz si ha ω ≈ 0.01676, b ≈ 0.0237, c ≈ 2.8e-4.
- Ordine di grandezza del drift (valore ipotetico, NON da fonte): con una tolleranza di 50 ppm tra due clock, a 48 kHz la deriva e' 2.4 frame/s, cioe' circa 8640 frame/h (0.18 s/h). Senza correzione, una FIFO tra due device si svuota o trabocca in minuti, da cui la necessita' di drift correction o resampling.

### Gaps
- Tolleranze tipiche in ppm dei clock audio consumer (codec integrato Mac, interfacce USB): non trovate in fonte affidabile.
- Algoritmo interno della drift correction degli aggregate device di macOS (tipo di resampler, banda, latenza aggiunta): non documentato da Apple nella pagina trovata.

## 7. Xrun (underrun/overrun): cause, rilevamento, recupero; priorita' dei thread su macOS (time-constraint policy, Audio Workgroups); scaling di frequenza della CPU; denormali e flush-to-zero

### Takeaway
Un xrun nasce sempre da un ciclo che supera il periodo: calcolo medio troppo pesante, picchi non limitati, blocchi, page fault, preemption, oppure buffer troppo piccoli per il jitter del sistema. Si rileva con i flag di stato (PortAudio), con discontinuita' del sample time e con le notifiche di overload (CoreAudio); si recupera continuando a girare e risincronizzando contatori, DLL e ring buffer. Su macOS il thread I/O e' gia' real-time (time-constraint policy). I thread ausiliari real-time vanno creati con la stessa policy e uniti all'Audio Workgroup del device (macOS 11+, quindi disponibile su Ventura) per informare il performance controller che decide frequenze e core. I denormali su x86 costano da decine a centinaia di volte di piu': nel thread audio si attivano FTZ/DAZ.

### Cited Findings
- "All sources of audio glitches within your code boil down to doing something that takes longer than the buffer period." — [Bencina 2011](http://www.rossbencina.com/code/real-time-audio-programming-101-time-waits-for-nothing)
- Flag PortAudio: `paInputUnderflow` (zeri inseriti per un underflow di input), `paInputOverflow` (dati di input scartati), `paOutputUnderflow` ("output data (or a gap) was inserted, possibly because the stream callback is using too much CPU time"), `paOutputOverflow`, `paPrimingOutput`; `Pa_GetStreamCpuLoad` e' di solito tra 0 e 1 "and it may exceed 1.0" — [PortAudio portaudio.h docs](http://files.portaudio.com/docs/v19-doxydocs/portaudio_8h.html)
- "If the client takes too long to produce output data, then the thread misses its deadline and we get an overload. The user hears this as a discontinuity, or a glitch" — [WWDC20 Meet Audio Workgroups](https://developer.apple.com/videos/play/wwdc2020/10224/)
- CoreAudio espone il selettore `kAudioDeviceProcessorOverload` (macOS, Mac Catalyst), accanto a `kAudioDevicePropertyIOStoppedAbnormally`; la pagina non descrive la semantica — [Apple, kAudioDeviceProcessorOverload](https://developer.apple.com/documentation/coreaudio/kaudiodeviceprocessoroverload)
- I buffer piu' piccoli sono "prone to dropouts as system load increases" — [NIME 2016](https://www.nime.org/proceedings/2016/nime2016_paper0005.pdf)
- Dopo un xrun il DLL del clock va reinizializzato (il codice di init gira "in the first process cycle when JACK starts, or after an xrun"); i loop di resampling adattivo devono ripartire se si perde la sincronizzazione, ma piccoli incidenti come cicli saltati non dovrebbero cambiare la latenza — [Adriaensen 2005](https://kokkinizita.linuxaudio.org/papers/usingdll.pdf), [Adriaensen, adaptive resampling](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)

#### Priorita' e Audio Workgroups su macOS
- `THREAD_TIME_CONSTRAINT_POLICY`: il thread dichiara di dover girare "for A cycles out of the next B cycles"; nell'esempio period = HZ/160 (6.25 ms), computation = HZ/3300 (circa 0.30 ms), constraint = HZ/2200 (circa 0.45 ms), preemptible = 1; il constraint "must be larger than the value for computation"; le unita' sono "Mach absolute time units"; "This is commonly used when interacting with CoreAudio"; un thread che mente sul carico puo' essere declassato a priorita' normale (Kernel Programming Guide, archivio 2013) — [Apple Kernel Programming Guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/KernelProgramming/scheduler/scheduler.html)
- Audio Workgroups: "a new feature available in macOS 11, iOS 14.0"; "a collection of real-time threads that work together to produce audio by a common deadline while spanning multiple processes"; "The system uses the audio workgroups to observe CPU usage of real-time threads so that it can better balance the competing interests of power consumption and performance"; "The I/O thread is the primary thread ... and it informs the kernel of the beginning and end of each work cycle"; "Only real-time threads can join an audio workgroup"; se si usa solo il thread fornito dal framework, non serve alcun lavoro — [Apple, Understanding Audio Workgroups](https://developer.apple.com/documentation/audiotoolbox/understanding-audio-workgroups)
- Thread paralleli: il workgroup si ottiene da `kAudioOutputUnitProperty_OSWorkgroup` (AUv2), da `AUAudioUnit.osWorkgroup` (AUv3) o, su macOS, direttamente dal device via HAL; `os_workgroup_join(wg, &token)` una volta per thread, `os_workgroup_leave` prima di uscire; errori `EALREADY` (thread gia' in un workgroup non annidabile) ed `EINVAL` (workgroup cancellato); ciclo tipico: attesa su un semaforo, lavoro, segnalazione di fine — [Apple, Adding Parallel Real-Time Threads to Audio Workgroups](https://developer.apple.com/documentation/audiotoolbox/adding-parallel-real-time-threads-to-audio-workgroups)
- WWDC 2020: "Modern CPUs have performance controllers, which make trade-offs between power consumption and computing power ... The performance controller can also dynamically change the clock frequency of the CPUs"; per i thread asincroni rispetto all'I/O si usano `AudioWorkIntervalCreate` e, a ogni ciclo, `os_workgroup_interval_start`/`finish` con scadenze in unita' `mach_absolute_time` (convertite con `mach_timebase_info`); `os_workgroup_max_parallel_threads` suggerisce quanti worker usare; "if you're wondering if you should create your own realtime threads, the answer is probably no ... measure everything" — [WWDC20 Meet Audio Workgroups](https://developer.apple.com/videos/play/wwdc2020/10224/)
- Risparmio energetico contro latenza: "the I/O buffer size will nearly always be the dominant factor affecting audio stack power usage"; con `kAudioHardwarePowerHintFavorSavingPower` OS X puo' aumentare la latenza (default da 512 a 4096 frame) — [Apple TN2321](https://developer.apple.com/library/archive/technotes/tn2321/_index.html)

#### Denormali
- Le operazioni su denormali sono piu' lente perche' gestite da un "software assist mechanism"; DAZ tratta come zero gli operandi denormali in ingresso, FTZ azzera i risultati denormali; sono bit del registro MXCSR (SSE) — [Intel oneMKL, Operating on Denormals](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2026-0/operating-on-denormals.html) (solo snippet di ricerca)
- Rallentamenti riportati: "a factor of 50 or so" (Mozilla); circa 12-13x a 64 bit e circa 19x a 32 bit senza FTZ/DAZ, circa 1x con FTZ/DAZ (Mixxx); "about two magnitudes larger" su Sandy/Ivy Bridge (arXiv) — [Mozilla bug 944143](https://bugzilla.mozilla.org/show_bug.cgi?id=944143), [Mixxx bug 1404401](https://bugs.launchpad.net/bugs/1404401), [arXiv 1506.03997](https://ar5iv.arxiv.org/html/1506.03997) (tutte solo snippet di ricerca)
- I flag sono per thread: impostarli in un costruttore e' inutile se il processing gira in un altro thread — [JUCE forum, Resolving denormal floats](https://forum.juce.com/t/resolving-denormal-floats-once-and-for-all/8241) (solo snippet di ricerca)
- Pattern scoped: impostare FTZ+DAZ all'ingresso di ogni `process()` e ripristinare lo stato all'uscita; costo: circa 7 bit di dinamica in fondo al range float, inudibili — [truce-core denormal.rs](https://docs.rs/truce-core/0.48.7/src/truce_core/denormal.rs.html) (solo snippet di ricerca)
- Rischio: con flush-to-zero globale possono emergere comportamenti inattesi, per esempio divisioni per zero perche' a − b = 0 con a != b — [Mozilla bug 944143](https://bugzilla.mozilla.org/show_bug.cgi?id=944143) (solo snippet di ricerca)

### Inferences
- Rilevamento in PGE: (a) leggere `statusFlags` (PortAudio) o confrontare `mSampleTime` successivi (CoreAudio): un salto diverso da `frameCount` indica un buco; (b) misurare la durata del callback con `mach_absolute_time` e tenere istogramma e massimo, non solo la media; (c) pubblicare sulla FIFO di ritorno i contatori di xrun, di eventi in ritardo e di grani scartati.
- Recupero: non fermare lo stream; reinizializzare il DLL, riallineare il read head dei grani rispetto al write head (marcando la discontinuita' nel buffer di cattura), applicare un breve fade per ridurre il click; se gli xrun si ripetono, ridurre il carico (meno grani o voci, come suggeriva gia' la descrizione di `Pa_GetCPULoad` nel paper del 2001) o aumentare il buffer.
- Budget di CPU: non ho trovato una regola numerica autorevole. Ragionevolmente il caso peggiore misurato del callback deve restare ben sotto il periodo, perche' il periodo include anche il risveglio cross-process di coreaudiod (vedi WWDC). Sotto 0.5-0.7 come carico di picco e' un margine prudenziale, da verificare empiricamente.
- [Intel/Ventura] L'API Audio Workgroups esiste (macOS 11+). Su Intel i core sono omogenei, ma il performance controller gestisce comunque la frequenza (Turbo Boost/SpeedStep), quindi unire i worker al workgroup e' innocuo e portabile su Apple silicon. Il guadagno effettivo su Intel non e' documentato.
- [Intel/Ventura] Su x86_64 l'aritmetica float passa per SSE, quindi FTZ/DAZ si impostano nel MXCSR (intrinsics `_MM_SET_FLUSH_ZERO_MODE` e `_MM_SET_DENORMALS_ZERO_MODE`, nomi da conoscenza generale, non verificati qui) all'inizio di ogni callback e nei worker. In alternativa o in aggiunta si iniettano rumore o DC minimi nei filtri ricorsivi e nei riverberi.
- [Intel/Ventura] Su Mac Intel `mach_timebase_info` restituisce tipicamente 1/1 (tick = ns), su Apple silicon un rapporto diverso. Dato da conoscenza generale non verificato in questa ricerca: va sempre usata la conversione.

### Gaps
- Semantica documentata di `kAudioDeviceProcessorOverload` e di come sottoscriverla (listener): la pagina Apple e' vuota; serve l'header `AudioHardware.h`.
- Valori raccomandati di period/computation/constraint per thread ausiliari su macOS moderno: non trovati. L'esempio del Kernel Guide (2013) e' illustrativo.
- Linee guida per il governor CPU su Linux (ArchWiki "Professional audio" bloccata da anti-bot): non raccolte; comunque irrilevanti per il Mac bersaglio.
- Il callback xrun di JACK (`jack_set_xrun_callback`) non e' stato verificato in fonte.

## 8. Microfono live su macOS: device diversi per input e output (aggregate, sample rate diversi, drift), permesso microfono (TCC) per applicazioni da terminale, Larsen, gain staging, DC offset

### Takeaway
Su macOS il full-duplex tra microfono e uscita su device diversi si fa con un aggregate device (un clock source, drift correction sugli altri) oppure con due IOProc/AUHAL, un ring buffer e un varispeed, accettando piu' latenza. Il lato input di AUHAL non converte il sample rate, quindi conviene far girare entrambi i device alla stessa frequenza. Il permesso microfono (TCC) segue l'app "responsabile": per un processo lanciato da Terminal il prompt e il permesso riguardano Terminal o iTerm. Se il permesso manca, il fallimento e' spesso silenzioso, con buffer a zero e nessun errore, quindi va rilevato attivamente. Il Larsen si previene in modo affidabile con le cuffie; con gli altoparlanti si mantiene un margine di 2-3 dB sotto il massimo guadagno stabile e si usano frequency shifting, notch e gate. Il DC si rimuove con un DC blocker a un polo.

### Cited Findings

#### Device diversi, sample rate, drift
- Aggregate device: in Audio MIDI Setup "Create Aggregate Device", spunta "Use" per i sotto-device (l'ordine definisce la numerazione dei canali), scelta del "Clock Source" e "Drift Correction" per ogni device che non e' il clock source (non per i device in word clock); alcune app non Apple richiedono un aggregate per usare input e output separati — [Apple Support, Aggregate Device](https://support.apple.com/en-us/102171)
- Sample rate sul lato input di AUHAL: l'AudioConverter interno gestisce solo conversioni "simple" di formato PCM, "Consequently, the device's sample rate should match the desired sample rate. If sample rate conversion is needed, it can be accomplished by buffering the input and converting the data on a separate thread with another AudioConverter." — [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html)
- Due device: due AUHAL, ognuno sul proprio IOProc, con notifica e passaggio dati (TN2091); CAPlayThrough: ring buffer piu' varispeed per il drift — [Apple TN2091](https://developer.apple.com/library/archive/technotes/tn2091/_index.html), [Apple CAPlayThrough](https://developer.apple.com/library/archive/samplecode/CAPlayThrough/Introduction/Intro.html)
- Esperienza riportata con aggregate privati: avviare il motore del microfono prima di creare l'aggregate, altrimenti le AirPods possono restare in A2DP "and the mic channel fails silently"; ospitare l'aggregate sull'uscita integrata invece che sull'uscita di default (post su process tap, anno non indicato) — [dev.to, 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)

#### Permesso microfono (TCC)
- Requisiti Apple: chiave `NSMicrophoneUsageDescription` in Info.plist ed entitlement `com.apple.security.device.audio-input` ("may record audio using the built-in microphone and access audio input using Core Audio"); "Your app needs to contain the appropriate key in its Info.plist file, and the appropriate entitlement enabled in macOS, before it requests authorization or attempts to use a capture device. Otherwise, the system terminates your app."; verifica con `AVCaptureDevice.authorizationStatus(for: .audio)`, prompt con `requestAccess(for:)`; "The system remembers the user's response to each access alert" — [Apple, Requesting authorization to capture and save media](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)
- Il microfono "requires the app to have both user text and entitlement", altrimenti l'app "will be crashed by macOS"; reset dell'intera categoria con `tccutil reset Microphone`; [Intel] i portatili Intel con chip T2 e quelli Apple silicon hanno la disconnessione hardware del microfono a coperchio chiuso, "There is no override for that protection." (3 marzo 2025) — [Eclectic Light, Managing privacy-protected devices](https://eclecticlight.co/2025/03/03/managing-privacy-protected-devices/)
- `tccutil` e' case-sensitive: si scrive `tccutil reset Microphone` con la M maiuscola (Quinn, Apple DTS) — [Apple Developer Forums 679303](https://developer.apple.com/forums/thread/679303) (solo snippet di ricerca)
- Attribuzione al terminale: per Processing su Catalina, che non otteneva mai il prompt, il workaround (marzo 2021) era lanciare l'eseguibile da Terminal (`/Applications/Processing.app/Contents/MacOS/Processing`), che "triggers the pop-up asking to access camera and mic" — [Processing Discourse](https://discourse.processing.org/t/audio-in-problem-with-mac-os-catalina/28897/7)
- Fallimento silenzioso di un binario CLI firmato (Claude Code 2.1.72, macOS Sequoia 15.x, marzo 2026): senza `com.apple.security.device.audio-input` "macOS silently denies microphone access — no TCC permission dialog is shown and no entry is created in the TCC database"; Terminal.app non compariva in Privacy & Security -> Microphone; `tccutil reset Microphone com.apple.Terminal` non aiutava — [GitHub anthropics/claude-code #33023](https://github.com/anthropics/claude-code/issues/33023)
- Caso analogo per la cattura dell'audio di sistema (process tap, servizio TCC diverso, `kTCCServiceAudioCapture`): tutte le chiamate restituiscono `noErr`, l'IOProc gira, "every buffer is zeros", senza errori o log; consiglio: verificare presto la presenza di campioni non nulli — [dev.to, 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)

#### Larsen (feedback acustico)
- Definizione: quando il segnale dell'altoparlante rientra nel microfono si crea un loop chiuso che "affects the system performance, deteriorating the sound quality and limiting the achievable amplification"; l'artefatto tipico e' l'howling ("Larsen effect"); la stabilita' si analizza con il criterio di Nyquist sul loop G·F (forward path per feedback path); il massimo guadagno stabile (MSG) definisce il limite; "a gain margin of 2–3 dB is recommended to avoid audible ringing effects" (Proc. IEEE 2011) — [van Waterschoot & Moonen, Fifty Years of Acoustic Feedback Control](https://ftp.esat.kuleuven.be/pub/sista/vanwaterschoot/reports/08-13.pdf)
- Metodi e numeri: i metodi manuali (scelta e posizione di microfono e altoparlante, notch sui modi, EQ a 1/3 d'ottava) danno +5-8 dB di MSG. Frequency shifting: i picchi della risposta di una stanza distano in media circa 10 Hz, quindi lo shift ottimo e' circa 5 Hz; sono riportati fino a +14 dB, ma il guadagno soggettivamente accettabile e' limitato a +6 dB per evitare battimenti, e uno shift di 5 Hz e' dichiarato inudibile per parlato e musica. Modulazione di fase o frequenza fino a +7 dB. Riduzione di guadagno automatica: AGC broadband, AEQ per sottobande, notch-filter howling suppression (NHS, il metodo piu' popolare; la maggior parte e' reattiva, cioe' l'howling si sente prima di essere rilevato); uno smoothing perfetto del loop gain darebbe al massimo circa +10 dB. AFC (cancellazione adattiva) ha il problema della correlazione tra segnale dell'altoparlante e sorgente — [van Waterschoot & Moonen 2011](https://ftp.esat.kuleuven.be/pub/sista/vanwaterschoot/reports/08-13.pdf)

#### DC offset
- DC blocker: `y(n) = x(n) - x(n-1) + R y(n-1)`, H(z) = (1 − z^-1)/(1 − R z^-1), con R tipicamente tra 0.9 e 1 e "for a 44.1 kHz sampling rate, R=0.995 is good"; si usa per togliere il DC che circola nei loop di delay line ed evitare che offset DC si accumulino — [J.O. Smith, DC Blocker](https://ccrma.stanford.edu/~jos/filters/DC_Blocker.html)

### Inferences
- [Intel/Ventura] Un motore lanciato da Terminal o iTerm come processo figlio: TCC attribuisce la richiesta all'app responsabile, cioe' l'emulatore di terminale. Il primo accesso mostra "Terminal would like to access the microphone" e il permesso, una volta dato, vale per tutto cio' che quel terminale lancia. Lanciato da un IDE, il responsabile e' l'IDE. Questa e' una deduzione dalle fonti comunitarie: la documentazione Apple ufficiale sul "responsible process" non e' stata trovata.
- Per PGE serve un controllo all'avvio: misurare l'RMS (o il conteggio di campioni diversi da zero) dei primi 0.5-1 s di input. Se e' esattamente zero, avvisare: "Abilita il microfono per <terminale> in Impostazioni di Sistema > Privacy e sicurezza > Microfono; per ripetere il prompt: `tccutil reset Microphone <bundle-id del terminale>`". Su Ventura il pannello si chiama "Impostazioni di Sistema" (rinominato da macOS 13; conoscenza generale).
- Un interprete o binario non firmato con hardened runtime potrebbe non essere soggetto al requisito dell'entitlement che ha colpito il binario CLI firmato del caso GitHub; un binario firmato con hardened runtime lo e'. Non verificato: va testato con l'interprete effettivamente usato.
- [Intel/Ventura] I process tap (`CATapDescription`, `AudioHardwareCreateProcessTap`) del post dev.to sono, per quanto noto, API introdotte con macOS 14.2 e quindi non disponibili su Ventura. Restano utili solo come conferma del pattern "permesso mancante = zeri silenziosi".
- Mic integrato con lo stesso clock dell'uscita integrata: preferire input e output con lo stesso sample rate (per esempio 48 kHz su entrambi). Con un'interfaccia USB come uscita e il microfono integrato in ingresso, usare un aggregate con drift correction sul device non master, sapendo che aggiunge un resampler (latenza e qualita' non documentate).
- Larsen in un granulatore live: le cuffie eliminano il percorso acustico e sono la mitigazione primaria. Con gli altoparlanti: microfono direttivo vicino alla sorgente e lontano dai diffusori; guadagno complessivo con 2-3 dB di margine sotto l'MSG; HPF/DC blocker in ingresso; gate o expander sull'input per non ricampionare il rumore di fondo; limiter in uscita. Pitch-shift dei grani e jitter di posizione agiscono come modulazioni che possono "spalmare" il loop gain (analogia con FS/PM, non verificata per i granulatori), ma una densita' alta di grani a pitch 1 con feedback tende a sostenere le risonanze della stanza. Opzione: notch adattivi (NHS) sull'uscita.
- Gain staging: lasciare headroom sul preamp del microfono (picchi del gesto strumentale ben sotto 0 dBFS), misurare il picco in ingresso nel callback e pubblicarlo via FIFO. Il clipping digitale in ingresso si propaga in tutti i grani che rileggono quel segmento del ring buffer. Nessuna fonte numerica raccolta (vedi Gaps).
- Il DC offset del microfono, se non rimosso prima di scrivere nel ring buffer, diventa un gradino a ogni attacco e rilascio di finestra di grano e un offset accumulato nella somma di molti grani. Il DC blocker (R ≈ 0.995 a 44.1 kHz, poco piu' alto a 48 kHz) va messo in ingresso, prima del ring buffer.

- Se `python3` (Homebrew, python.org o pyenv) richieda l'entitlement `audio-input` sotto Ventura: non verificato.
- Valori raccomandati di headroom e gain staging (dBFS) per l'ingresso microfonico: nessuna fonte affidabile raccolta.
- Latenza e algoritmo della drift correction degli aggregate device: non documentati nella fonte Apple trovata.
- Comportamento del microfono integrato dei Mac Intel con elaborazione vocale di sistema (noise reduction) e suo effetto sulla latenza: solo un accenno non verificato (vedi sezione 2).
